Plugins

start runs a loopback-only, token-guarded control server that both braid's own built-in functionality and external plugins register routes, static files, and process lifecycle listeners on.

Using plugins

List a plugin by package name/path in plugins — optionally as a [name, options] tuple. Options must be plain data (strings, numbers, booleans, arrays, plain objects, and also RegExp, Date, Map and Set), since a background daemon receives them as a structured-clone copy. A function in options makes braid start fail with a clear error:

export default defineConfig({
	processes: [ /* ... */ ],
	plugins: [
		"@your-scope/braid-plugin-something",
		["./plugins/local-plugin.js", { port: 4100 }],
	],
});

No dynamic discovery — if it's not listed, it doesn't run. A plugin is resolved from the config file's own location, so it's found in your project's node_modules, not braid's. braid's own internal core plugins (/api/status; per-process log persistence behind braid logs; the /api/processes/stop, /api/processes/restart and /api/processes/start routes behind braid stop/restart/start <name>; and /api/shutdown behind a bare braid stop) aren't configurable and aren't listed in plugins. @aip-tech/braid-plugin-ui is the first real external plugin built against this API — a web dashboard with live status and stop/restart buttons.

Building a plugin

A plugin is an object matching BraidPlugin:

import type { BraidPlugin } from "@aip-tech/braid";

export const helloPlugin: BraidPlugin = {
	name: "hello",
	register(ctx, options) {
		ctx.registerRoute("GET", "/hello", (req, res) => {
			res.writeHead(200, { "content-type": "text/plain" });
			res.end("hello from a braid plugin");
		});

		ctx.on("processCrash", (event) => {
			ctx.log(`"${event.name}" crashed (code ${event.code})`);
		});
	},
};

export default helloPlugin;

register() can be async. A plugin that throws or rejects during register() is logged and isolated — it doesn't take down the manager or any other plugin. Runs in-process with full Node access, the same trust level as any other dependency in your node_modules — there's no sandboxing beyond that.

The PluginContext API

Passed to register(ctx, options), one instance per plugin:

  • registerRoute(method, path, handler) — a plain node:http handler on the shared control server. Throws if that method+path is already taken by another plugin.
  • registerStatic(prefix, dir) — serves files under dir for any request path starting with prefix. Throws if the prefix is already taken.
  • registerUpgrade(path, handler) — raw HTTP Upgrade dispatch (e.g. for a WebSocket) on an exact path match. A handler that throws or rejects is logged and its socket destroyed; it never takes the daemon down.
  • on(type, handler) — subscribes to a process lifecycle event, see below.
  • getProcesses() — the current { name, pid, alive, startedAt?, cpu?, memory? }[] for every configured process, the same data status renders — including one with autoStart: false that's never been started (pid/startedAt absent, alive: false). cpu/memory are likewise absent until the daemon's first sample, or while a process is stopped.
  • stopProcess(name) — stops one named process. Resolves "ok", "unknown" (not configured, or not currently running), or "busy" (a restart is already in progress for it).
  • shutdown() — stops every process and shuts the daemon down, the same orderly way braid stop does. Returns immediately. Ignored (and logged) if called during register(), before the daemon is up.
  • restartProcess(name) — stops and respawns one named process, then runs its own onRestart hook (if any) and cascades to dependsOn dependents exactly as a watch-triggered restart would. Can take a while to resolve if onRestart keeps retrying. For a process that hasn't been started yet (still waiting on its own startAfter, or autoStart: false), it starts it exactly as startProcess would, with no cascade. Resolves "ok", "unknown", or "busy".
  • startProcess(name) — starts a configured process that isn't currently running; the counterpart to restartProcess for one that's stopped or has autoStart: false and has never run. Idempotent: resolves "ok" as a no-op if it's already alive, rather than killing and respawning it the way restartProcess would. A genuine first start doesn't cascade to dependsOn dependents the way a restart does, but does honor the process's own startAfter if it sets one.
  • log(message) — writes a line to stderr, prefixed with this plugin's own name. If sent before the daemon's ready handshake (e.g. from a controlServerReady handler), also relayed straight to the terminal that ran braid start, not just daemon.log.

stopProcess/restartProcess/startProcess/shutdown are available to every plugin, not only ones that registered the affected process themselves — a plugin can stop, restart, or start any configured process. Same trust level as any other capability in your node_modules, worth knowing before wiring one up to something you didn't write yourself.

The control server itself is loopback-only (127.0.0.1). It rejects a request whose Host isn't a loopback name (421), which defeats DNS rebinding, and a non-GET request or upgrade whose Origin doesn't match the page it was served from (403), which stops another site, or another local port, from driving it. Only the hostname is checked, so it still works through an SSH tunnel or a devcontainer port forward. It also requires a bearer token on every request (a per-run secret written to the pidfile) — enforced automatically for every route, a plugin's own handler doesn't need to check it. The token is accepted only as an Authorization: Bearer header: never as a cookie or a query parameter. Static files are the exception, served without it; see Serving browser content if you're building something a browser loads directly.

Lifecycle events

EventPayloadFires when
processStart{ name, pid }A process is first forked.
processExit{ name, code, signal }A process's underlying child exits.
processCrash{ name, code }A process crashes (or fails to start) — the whole stack is about to shut down.
processRestart{ name }A watch-triggered restart happened internally, not exited. A manual (restartProcess/braid restart <name>) or dependsOn-cascade restart shows up as a plain processExit+processStart pair instead, not this event.
processOutput{ name, stream, chunk }Raw stdout/stderr bytes from a process, already line-prefixed.
daemonShutdown—The daemon is shutting down — the last chance to clean up (e.g. end open connections) before the control server closes.
controlServerReady{ port, token }Fires once, after the control server is listening and every plugin has finished register()'ing — the earliest point a plugin can know its own reachable port/token (register() itself runs before the port is known). Useful for logging a browser-openable URL for content served via registerStatic.

Every listener is isolated: a synchronous throw or a rejected promise from one plugin's handler is logged, not left to crash the manager or block other plugins' listeners for the same event. Route and upgrade handlers are isolated the same way. As a last resort, any error nothing catches stops every process cleanly and is logged to .braid/daemon.log, instead of killing the daemon and leaving its processes orphaned.

Serving browser content

Files registered with registerStatic are served without the token, since a page can't put a header on its own <script> and <link> loads. Treat a static directory as public: put nothing secret in it. Routes and upgrades still need the token.

To give a page the token, log its URL with the token in the fragment, http://127.0.0.1:<port>/#token=<token>, from a controlServerReady listener. Browsers never send a fragment to any server. The page reads it from location.hash, keeps it in sessionStorage, strips it from the address bar with history.replaceState, and sends Authorization: Bearer <token> on its own fetch() calls.

A browser can't set headers on a WebSocket, so for an upgrade the page first calls POST /api/ws-ticket (with the header) to get a single-use ticket, valid for 30 seconds, and connects with ?ticket=<ticket>.
